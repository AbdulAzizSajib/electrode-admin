## Why

`src/lib/api/orders.ts`, `payments.ts`, `shipments.ts`, and `shipping-methods.ts` are still in-memory mocks, and — like `purchase-orders.ts` before it — `orders.ts` in particular models capabilities the real backend doesn't have: an admin "create order" action (orders only ever come from customer checkout — there is no admin-create endpoint at all) and a strict single-file-forward fulfillment sequence the real status-update endpoint doesn't enforce. This is the next roadmap step after `integrate-inventory-api` — swap all four to the real backend and correct the order lifecycle to match what the backend actually allows an admin to do.

## What Changes

- Replace every function body in `src/lib/api/orders.ts`, `payments.ts`, `shipments.ts`, `shipping-methods.ts` with real `fetch` calls, following the established `request<T>()` envelope pattern.
- **BREAKING** (internal only): reshape each type:
  - `Order`: `fulfillmentStatus` → `status` (`PENDING | CONFIRMED | PROCESSING | SHIPPED | DELIVERED | CANCELLED | COMPLETED` — 7 values, not the mock's 5); **no `paymentStatus` field at all** — the real `Order` has none; payment state only exists per-`Payment` record, never rolled up onto the order. `total`/`discount`/`shippingCost`/`tax` → `totalAmount`/`discountAmount`/`shippingAmount`/`taxAmount` (Decimal-as-string, see `integrate-products-api` design.md). `customerName`/`customerEmail` (hand-joined by the mock) become an embedded `customer: {id, firstName, lastName, email, phone}` object — no separate user lookup needed. `shippingAddress` becomes a nullable, differently-shaped `CustomerAddress` object (`addressLine1`/`addressLine2` instead of `line1`/`line2`, `phone` required, `state`/`postalCode` optional). `statusHistory` entries become `{fromStatus, toStatus, note, changedById, createdAt}` instead of the mock's `{status, at, note}`. Items add `variantId` and switch `unitPrice`/`totalPrice` to Decimal-as-string.
  - **There is no admin "create order" capability, at all** — checkout (`POST /orders`) always operates on the calling user's own cart; there's no payload shape that lets an admin place an order on a customer's behalf. `orders.ts` drops any create function (it never had a create UI anyway, so no page changes needed there).
  - **The dedicated `PATCH /orders/:id/cancel` endpoint is customer-self-service only** — it always resolves the caller's own `Customer` record and 404s if the order isn't theirs, with no staff bypass. Admin "cancel" is done through `PATCH /orders/:id/status` with `status: CANCELLED`, the same endpoint as every other status change. `orders.ts` drops the separate cancel function/hook.
  - `updateOrderStatus` (real) does **not** enforce a forward-only sequence — it only rejects setting the same status again. The order detail page's single "Mark as next status" button (driven by the mock's `FULFILLMENT_SEQUENCE`) becomes a plain status `Select` offering all 7 values.
  - `Payment.method` is `COD | CARD | BKASH | NAGAD | ROCKET | STRIPE | PAYPAL | BANK_TRANSFER | OTHER` (9 values, not the mock's 4); `amount` is optional on create (defaults server-side to the order's full `totalAmount` when omitted) but the form keeps it as a required, pre-filled-with-balance-due input for clarity; `status` is settable at creation (defaults `PENDING` server-side; the form defaults it to `PAID` to match the mock's "recording a payment means it's confirmed" behavior). No update/void endpoint exists for a recorded payment — matches the mock (payments were create-only there too).
  - `Shipment` create and update are **separate endpoints** (`POST` 409s if one already exists; `PATCH` 404s if none does), not the mock's single upsert — the admin UI keeps one dialog but picks the verb client-side based on whether a shipment is already loaded. `status` is an 8-value enum (`PENDING | PROCESSING | SHIPPED | IN_TRANSIT | OUT_FOR_DELIVERY | DELIVERED | FAILED | RETURNED`); `shippedAt`/`deliveredAt` are settable via update. No order-status side effect — creating/updating a shipment no longer auto-advances the order's status (the mock's `_advanceOrderToShipped` goes away); staff set both independently, matching the real backend's lack of any such linkage.
  - `ShippingMethod` gains `estimatedDays?` (not in the mock); `description` becomes optional (was required); `price` becomes Decimal-as-string.
- Update `orders-list-page.tsx`: drop the Payment column (no per-order payment status to show without an extra fetch per row — the order-list endpoint doesn't embed payments); status filter/badges cover all 7 values; search only matches order number server-side (the real endpoint's `searchableFields` is `["orderNumber"]` only, not customer name/email like the mock searched).
- Update `order-detail-page.tsx`: status `Select` instead of "mark next" button; drop the separate cancel button (folded into the status `Select`); payment amount/method/status fields for the new enum and required-amount-with-status; shipment dialog issues create vs. update based on whether one exists; render the real `statusHistory`/`shippingAddress`/`customer` shapes.
- Update `shipping-methods-page.tsx`: `description` optional, add `estimatedDays` input, drop the `_isShippingMethodReferenced` pre-delete check (see design.md — the real delete endpoint has no friendly conflict handling to surface either way, so the check wasn't buying accuracy).

## Capabilities

### New Capabilities
- `order-fulfillment`: order visibility and status management, payment recording, shipment tracking, and shipping-method configuration, backed by the real endpoints — explicitly scoped to what an admin can actually do (view, update status, record payments, manage shipment), since order creation is a customer-checkout-only capability this admin panel doesn't perform.

### Modified Capabilities
(none)

## Impact

- **Code**: `src/lib/api/orders.ts`, `payments.ts`, `shipments.ts`, `shipping-methods.ts` (mock → real fetch); `src/features/sales/orders/orders-list-page.tsx`, `order-detail-page.tsx`, `src/features/sales/shipping-methods/shipping-methods-page.tsx`.
- **Depends on `integrate-products-api`** (order items reference real products) and **`integrate-inventory-api`** (checkout deducts real `Stock`, though checkout itself isn't part of this change).
- **Backend dependency**: `{{base_url}}/orders`, `/orders/:id/payments`, `/orders/:id/shipment`, `/shipping-methods` must be reachable.
- **`_getAllOrders()`/`_getOrderById()` need the same compatibility shim `_getAllProducts()`/`_getAllWarehouses()` got**: `dashboard.ts`, `customers.ts`, `refunds.ts`, and `returns.ts` (none touched by this change) all read one or both synchronously. `_setOrderPaymentStatus()`/`_advanceOrderToShipped()`/`_isShippingMethodReferenced()`/`_getAllShippingMethods()` have no consumers outside the four files this change migrates together, so they're removed outright.
- **Field renames ripple into the four shim consumers**: `dashboard.ts` and `customers.ts` reference `o.fulfillmentStatus`/`o.total`; `returns.ts` references `o.fulfillmentStatus`; `refunds.ts` references `o.paymentStatus`, which no longer exists on `Order` at all (payment state lives on `Payment` records now) — see design.md for the minimal fix to each.
